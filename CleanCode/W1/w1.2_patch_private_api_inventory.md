1. 文档目的

本文档盘点当前 vllm-gr 对 vLLM、vLLM-Ascend 和 LMCache 的运行时修改，以及这些修改依赖的私有或不稳定上游 API。

本任务只建立事实基线，不调整生产代码，不改变 Beam Search、Scheduler、ModelRunner、Attention、Catalog 或 OpenAI Serving 的现有行为。

该基线用于支持后续工作：

判断每个 Patch 是否仍然必要；

明确 Patch 在什么进程、平台和功能条件下安装；

识别普通非 Beam 请求受到的全局影响；

在上游版本升级时快速定位兼容风险；

为 W2–W7 的移除、收窄和重构提供验收依据；

防止新增未经登记的 Monkey Patch 或私有 API 依赖。

3. 盘点范围

3.1 In Scope

vLLM general plugin 自动激活链路；

vllm_gr/patch.py 触发的生产运行时 Patch；

EngineArgs、OpenAI Serving、EngineCore Client、EngineCore、Scheduler、ModelRunner 和 Attention 注册修改；

LMCache 兼容 Patch；

Benchmark-only Patch；

动态字段、全局注册表、字符串配置协议和 import-order 假设；

3.2 Out of Scope

兼容版本矩阵；

修改或删除任何现有 Patch；

引入 Patch Registry；

重构生产目录；

修复已识别的行为问题；

性能优化；

改变 Beam 排序、EOS、Length Penalty 或输出语义。

4. Patch 单元定义

本文不按每一次赋值统计 Patch，而按“能够独立安装、验证、失败或移除的一组行为扩展”统计。

例如，以下三个替换属于同一个 GPU ModelRunner Patch 单元：

GPUModelRunner.execute_model = patched_execute_model
GPUModelRunner._prepare_inputs = patched_prepare_inputs
GPUModelRunner._bookkeeping_sync = patched_bookkeeping_sync

因为它们：

一起安装；

服务同一个 Beam execution capability；

必须保持一致；

后续应由同一个 GPU ModelRunner Adapter 替代。

5. 总体结论

当前基线可归纳为：

1 个运行时激活边界；

14 个生产运行时 Patch/全局修改单元；

1 个 Benchmark-only Patch 集合；

7 类私有或不稳定上游 API 依赖边界。

静态 Patch 单元数量和 B01 目标已由上述固定源码确认。P14 因缺少 LMCache 固定版本尚未达到可执行 compatibility baseline；第 12.2/12.3 节的机器清单和完整性测试也仍是建议项，不应视为已经落地。因此本文已建立 vLLM/vLLM-Ascend/vllm-gr 的事实基线，但 W1.2 的 CI governance acceptance 尚未全部满足。

其中风险最高的是：

EngineCoreRequestType 运行时 Enum 扩展；

EngineCore socket loop 和进程入口替换；

Scheduler.schedule 替换；

GPU/NPU ModelRunner 私有热路径替换；

LMCache 内部生命周期方法替换。

7. 生产运行时 Patch Inventory

7.0 安装角色与消费角色

下列条目原有的 Process roles 主要描述 Patch 的功能消费位置，不等于当前代码的实际安装尝试位置。当前 vLLM 0.22.1 会在 Main、EngineCore subprocess 和 Worker subprocess 调用 general plugin；vllm_gr.plugin.register() 又在每个进程调用 re_apply_patches(force=True 路径)。

因此当前实际安装基线是：

P01、P03–P13：在 Main、EngineCore 和 Worker 中都会尝试安装，最终是否成功取决于 import-order、可选依赖和平台。P08–P12 由 P04 的 patch_batch_and_fork() 间接触发。

P02：只在 current_platform.device_type == "npu" 时尝试包装 NPUWorker.init_device，但类修改也可能先发生在 NPU Main/EngineCore 进程；真正消费位置是 NPU Worker。

P11：即使当前平台是 NPU，只要 GPUModelRunner 可导入也会修改该类；“Platforms: GPU”表示执行热路径，不表示安装时有 GPU capability gate。

P12：只有 is_npu_available() 为真且 NPUModelRunner 可导入时安装。

P14：只有 VLLM_GR_LMCACHE_PATCH 为真或 sys.argv 含 LMCacheConnectorV1 时尝试安装；环境变量会随子进程继承，因此可能在多个进程重复执行。

P13：在 P01 导入 BeamAttentionBackend 时即通过 decorator 修改 CUSTOM registry，不需要等到 P04/P11/P12。

后续机器可读清单应把 install_roles 和 execution_roles 分开；在此之前，各条目的 Process roles 按“主要执行/消费角色”解释。

W1.2 完成时应满足：

所有生产运行时 Patch 都有唯一 ID；

Benchmark-only Patch 与生产 Patch 分离；

每个 Patch 记录 source、target、process role、platform 和 required condition；

每个 Patch 明确普通请求影响；

每个 Patch 明确幂等、恢复和失败行为；

所有私有 API 按边界分类；

Critical 私有 API 有现有验证或明确缺口；

每个 Patch 有 owner 和 removal criteria；

Open PR 只作为 planned replacement，不与 current baseline 混淆；

新增未经登记的 Patch 可被 CI 检测；

本任务不改变任何生产算法或运行时行为。
